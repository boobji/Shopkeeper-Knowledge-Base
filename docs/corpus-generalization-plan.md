# 通用化改造方案：从「万用表 RS-12」到「任意商品说明书」

> 目标：让导入链路不再依赖"文档恰好结构良好"这个隐式前提。
>
> **状态：P0 四项已实施**（2026-09-07），P1 待排期。
> 落地文件：`knowledge/domain/structure_aware.py`（P0-1）、
> `knowledge/domain/chunk_clean.py` + `nodes/chunk_clean_node.py`（P0-2/P0-3）、
> `nodes/item_name_recognition_node.py` + `prompts/item_name_prompt.py`（P0-4），
> 全部受 `ImportConfig` 的环境变量开关控制，可一键关闭回退旧行为。
> 回归情况：`tests/test_p0_generalization.py` 24 个用例 + 全量 141 个用例通过。

---

## 一、问题定性

**并不是代码里对 RS-12 写了 `if` 判断**，而是整条链路隐含了一个前提：

> 输入是"有文本层、单一品类、结构清晰、纯中文"的技术手册。

RS-12 恰好完美满足这个前提，所以看起来哪儿都对；家电说明书普遍不满足，于是全线塌方。
这类问题的特点是：**没有一行代码写错，但整套假设失效**。

## 二、实测证据

### 2.1 语料侧：79% 是纯扫描件（无文本层）

对下载的 28 本中文家电说明书逐个做文本层探测：

| 判定 | 数量 | 说明 |
| --- | --- | --- |
| **纯扫描影印，0 文本层** | **22 本（79%）** | 页内全是图片，必须靠 OCR |
| 有文本层 | 6 本 | 002 / 011 / 024 / 032 / 034 / 065 |

示例：`035_咖啡机.pdf` 共 19 页，pypdf 提取全部为空 —— **没有任何文字，全是图**。

### 2.2 链路侧：一切都建立在 Markdown 标题之上

`document_split_node._split_by_headings()` 的切分**只认 `#` 标题**：

```python
heading_re = re.compile(r"^\s*(#{1,6})\s+(.+)")
```

| 文档 | 解析后二级标题数 | 切块结果 | 硬切率 |
| --- | --- | --- | --- |
| RS-12（有文本层） | **20 个**（安全手册 / 控制与端口 / 直流电压测量 …） | 21 块，每块一个语义章节 | **0%** |
| 扫描件（预计） | 大量缺失 | 退化成按字数切 → `标题-1/-2/-3` | 偏高 |

一旦标题缺失，`title` 会降级成 `file_title` 或 `file_title-N`，此时：

- 切块失去语义边界 → 检索召回的段落与问题不在同一主题
- `item_name_recognition_node` 取**前 K 块**做商品名抽取 → 抽到的是封面/安全套话
- 图谱节点按 chunk 抽实体 → 实体来自混合多个主题的流水文本

### 2.3 内容侧：噪音比想象的多

| 现象 | 实例 | 影响 |
| --- | --- | --- |
| 中英双语混排 | 024 微波炉目录：`简明操作指南 .... Quick Guide to Operation ( 简明操作指南 )` | 中文占比仅 7%，embedding 被稀释 |
| 目录页点线索引 | `微波炉的放置 ......................... 12` | 索引页无信息量却占 chunk |
| 通用安全套话跨文档重复 | 065：`本产品不打算由儿童或有体力、感官或精神缺陷的人使用…` | 多商品都命中同一段 → **跨文档误召回** |
| 客服营销内容占据前几页 | 032：海尔「1+5 成套服务」承诺 | 商品名抽取容易被干扰成"海尔产品" |

## 三、失配点清单

| # | 环节 | 隐含假设 | 现实 | 后果 | 严重度 |
| --- | --- | --- | --- | --- | --- |
| 1 | PDF 解析 | 有文本层 | 79% 纯扫描 | 版面结构靠 OCR 重建，标题丢失 | 高 |
| 2 | 标题分块 | 有 `#` 层级 | OCR 后标题大量缺失 | 退化硬切，语义边界消失 | 高 |
| 3 | 商品名抽取 | 前 K 块含品名 | 前 K 是封面/套话/营销 | 抽到模糊名或回退文件名 | 高 |
| 4 | 语言假设 | 纯中文 | 中英混排、符号表格多 | 检索被外文稀释 | 中 |
| 5 | 内容去重 | 文档内容独立 | 安全套话跨商品重复 | 跨文档误命中、评测失真 | 中 |
| 6 | 表格线性化 | 表格规整 | OCR 表格结构错乱 | `<table>` 线性化后语义破碎 | 中 |
| 7 | 提示词示例 | 仪器类设备 | 示例全是万用表/示波器/PLC | 领域偏移，抽取偏仪器侧 | 低 |

> 提示词**不是**主因。`ITEM_NAME_SYSTEM_PROMPT` 的示例为
> 「UT890D+万用表 / MS02000B 示波器 / SIMATIC S7-1200 / Catalyst 9300 交换机」，
> 全部是仪器设备，对家电有领域偏移，但规则本身通用——顺手改掉即可，优先级低。

## 四、改造方案

按投入产出排序。**建议先做 P0，四项都不改现有切块逻辑，属于增量增强。**

### P0-1 结构感知的多级降级分块 ★最高优先

**现状**：只有"按 `#` 标题切"一条路，失败就硬切。

**改法**：三级降级，逐级兜底。

```
① 标题层级完好（硬切率 < 10%）        → 现有 _split_by_headings，不动
② 标题稀疏   （10% ≤ 硬切率 < 40%）   → 用 MinerU 中间产物补结构
③ 标题几乎缺失（硬切率 ≥ 40%）        → LLM 语义分段 + 标题补全
```

**关键抓手：`*_content_list.json`**。MinerU 生成的中间产物带有**版面信息**，比 Markdown 更可靠：

```json
{"type": "text|header|table|image|footer|page_number", "bbox": [...], "page_idx": 0}
```

RS-12 实测：200 条 = text 148 / header 18 / table 3 / image 13 / footer 9 / page_number 9。
即使 Markdown 丢失了 `#`，也能靠 `type=header` + `bbox` 的**字号、位置、加粗**还原章节层级。

- 落地位置：新增 `knowledge/processor/import_process/nodes/structure_aware_split_node.py`，
  或扩展现有 `document_split_node.py` 的 `_split_by_headings`
- 工作量：中（1~2 天）
- 收益：**解决 79% 扫描件的结构问题**，是根因层面的修复

### P0-2 通用样板段去重

不看 embedding，用**字符 n-gram 相似度**就能抓到重复套话（成本极低）：

- 导入时维护跨文档的"高频样板段指纹库"（SimHash / MinHash / n-gram 集合）
- 命中的段落：折叠为一条 + 降权，或直接剔除并打 `boilerplate` 标记
- 检索时对 `boilerplate=true` 的块降权

- 落地位置：`document_split_node` 之后新增清洗节点，或并入 `_assemble_chunk`
- 工作量：小（半天）
- 收益：直接消掉"问 A 商品召回 B 商品安全声明"这类 badcase

### P0-3 语言/噪音过滤

在 chunk 级计算中文字符占比：

| 中文占比 | 处理 |
| --- | --- |
| ≥ 30% | 正常入库 |
| 10% ~ 30% | 入库但打 `lang=mixed`，检索降权 |
| < 10% | 判定外文页/纯符号页，**不入库** |

同时对**目录页**（连续 6 个以上点线符 `.` `·` `…`）直接剔除。

- 注意：Symbol 多的技术页（如 RS-12 的规格表）中文占比会偏低，**阈值需按文档类型可调**，
  写进 config 而不是硬编码
- 工作量：小（半天）

### P0-4 商品名抽取的采样与提示词

**采样从"取前 K 块"改为"结构优先采样"**：

1. 文档标题 + 前 2 个有内容的块（跳过纯图片块）
2. 命中型号正则的块（`[A-Z]{2,}[- ]?\d{2,}[A-Z]?` 形如 RS-12 / UT890D / S7-1200）
3. 正文前 10% 中出现频次最高的品类名词
4. 以上都没有才回退文件名

**提示词**：把 4 条仪器示例替换成**跨领域的 2~3 条 + 通用规则**（品牌/型号/品类三层，缺哪层降哪层）。

- 落地位置：`item_name_recognition_node._prepare_item_name_context()` + `knowledge/prompts/item_name_prompt.py`
- 工作量：小（半天）
- 收益：不再出现"海尔产品""UNKNOWN 回退"这类问题

### P1-5 章节类型打标 + 意图路由

给每个 chunk 打 `section_type`：`safety / spec / operation / maintenance / troubleshooting / warranty`

- 问「怎么清洁滤网」→ 优先 `maintenance`，屏蔽 `safety`
- 问「功率多大」→ 锁定 `spec`

- 落地位置：抽取节点打标 → `import_milvus_node` 写入标量字段 → 检索侧过滤表达式
- 工作量：中（1 天）

### P1-6 Parent-Child 检索

针对 OCR 流水文（一段里塞了多个主题）：

- 存储**小块**（命题级，200~300 字）用于精确召回
- 返回**父块**（章节级）给 LLM 保证上下文完整

项目已有 `child_chunk_node.py`，可直接扩展。

### P1-7 评测按文档类型分组

现有 `eval/retrieval_eval_set.json` 是单一商品。改造后按 **有文本层 / 扫描件** 分组统计 Recall@K，
避免整体指标掩盖扫描件上的塌方。

### P2-8 MinerU 参数与 OCR 语言

确认 OCR 语言参数是中文（`-l ch` / `--lang ch`），并对比 `pipeline` 与 `vlm` 后端在该类说明书上的
版面还原率。这一项是上游参数，改起来便宜且影响面大，**建议排在实际动刀前先验证**。

## 五、立即可用的工具

### `scripts/diagnose_chunks.py` — 切片质量体检

导入后跑一次，量化"这个文档到底切得好不好"，替代凭感觉调参：

```bash
python scripts/diagnose_chunks.py <chunks.json>
python scripts/diagnose_chunks.py --dir knowledge/temp_data/20260906
python scripts/diagnose_chunks.py --dir knowledge/temp_data -o eval/reports/chunk_health.md
```

输出指标：硬切率 / 无标题率 / 碎片率 / 低中文占比 / 目录页率 / 跨文档重复样板段；
超出阈值会给出明确的归因建议，并在退出码上体现（便于接入 CI 卡质量）。

实测基线：

```
文档                                     块数   硬切   无题   碎片   低中   目录
万用表RS-12的使用_new                      21    0%    5%    5%   24%    0%
HUAWEI Matestation B520 用户手册           31    0%    3%   29%   10%    0%
```

（RS-12 硬切率 0% = 结构完好，印证上述判断；其"低中 24%"源于规格表里大量单位符号，
属于阈值需要按文档类型放宽的情形。）

### 语料筛选建议

演示用优先选**有文本层**的 6 本：`002 面包机 / 011 咖啡机 / 032 微波炉 / 034 微波炉 / 065 搅拌器`，
外加 `024 微波炉`（有文本层但中英混排，正好当多语言改造的测试用例）。
纯扫描件先把 P0-1 做了再上。
